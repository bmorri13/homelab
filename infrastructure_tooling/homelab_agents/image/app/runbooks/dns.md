# DNS detections (possible tunnelling, NXDOMAIN burst, zone transfer or ANY query, watched services, first LLM API or geolocation lookup)

Source: `index=network sourcetype=adguard:querylog`, AdGuard Home's query log. AdGuard only logs: nothing is blocked, so a query in the log was answered. Fields: `QH` (name), `QT` (type), `IP` (client, the finding's `src`), `Answer` (base64 DNS reply), `Cached`, `Upstream`. Names ending in `.tail<id>.ts.net` are clients appending the tailnet search domain, not separate lookups. `object` is the registered domain (or the first few domains or names).

Check:
- All of the client's DNS around the time: `index=network sourcetype=adguard:querylog IP="<src>" earliest=-1h latest=+1h | stats count values(QT) dc(QH) by QH | sort - count`, and whether it has done the same before (look back 7 days). A pattern that repeats daily from one device for weeks is usually software, not an intrusion.
- Tunnelling: look at the sample names. Random-looking labels, base32/hex/base64 text, or a counter in the name under one domain, from one device, look like data carried in DNS. A vendor's reputation or telemetry domain (antivirus, CDN, DNSBL) doing the same is benign: say which domain and suggest adding it to the `hl_dns_chatty_domain` macro in `85_detections`. Who owns the domain (well-known vendor or a fresh, unknown one) matters most.
- NXDOMAIN burst: are the failing domains random-looking strings (DGA) or real names that went away (an app pointed at a dead service, a typo, a misconfigured search domain)? A device that keeps trying random domains is likely infected.
- Zone transfer or ANY: which names were asked for, and from which device. `dig`, `nslookup` or `host -a` run by the owner looks like this; a device that isn't someone's workstation asking for zone transfers is reconnaissance.
- Data-drop or callback service (`object` is the category: webhook, callback, paste, filedrop, tunnel, tor; the domains are in `detail`, the list is `hl_dns_watch_domains.csv` in `85_detections`). Webhook and callback lookups are the serious ones: a request-capture URL is where stolen output gets posted, and an out-of-band callback name (Interactsh `oast.*`, `interact.sh`, Burp Collaborator, dnslog) is how a blind injection proves it ran, so the client may be the victim of an exploit rather than the attacker. Look at the names: a token-like label under the callback domain, plus a marker of a known security scanner, from a CI or scanner job, is expected; say so and suggest an `hl_dns_watch_allowed` entry for that marker on the Splunk host (not the address: pods change addresses). A callback name from a server or application pod with no scan running means something processed attacker input: find which service, and what request reached it just before. Paste, file-drop and tunnel lookups from a workstation during the owner's own work are usually benign; from a server or pod they are not. Tor: someone downloaded Tor or opened the Tor Project site.
- Tor category with the Splunk host (security-tooling-01) as the client: `hl-threat-feeds.service` there downloads the Tor exit list from `check.torproject.org` every 6 hours and 5 minutes after boot, so that host looking up that one name is the threat-feed job, not Tor in use. Confirm with the job's own line within a few minutes of the lookup: `index=infra host=security-tooling-01 syslog.identifier=hl-threat-feeds "threat feed:" "feed=tor"`. If it is there and `check.torproject.org` is the only Tor Project name the client looked up: expected_activity, and suggest an `hl_dns_watch_allowed` entry for that client and exactly that name (not the `tor` category or all of `torproject.org`). Any other Tor Project name from it, or no feed line at that time, is checked like any other client.
- First lookup of an LLM API or IP geolocation service by a client (`object` is the host name). The lab's agents and some hosts call LLM APIs daily, so a pair is only new when a client is new or changed what it does. A pod address (the pod range not yet in `hl_dns_llm_client_ignore`) is most likely an agent run; say so and suggest setting the macro on the Splunk host. Otherwise: what runs on that client, did someone install an AI tool or agent, and is it a provider nothing here uses (DeepSeek, Zhipu GLM, Moonshot Kimi, xAI, resellers)? An agentic attack framework looks like a new LLM API client plus bursts of scanning, login attempts or geolocation lookups (`api.db-ip.com`, `ipinfo.io`, ...) from the same client. A geolocation lookup alone, from a device that checks its public address (a DDNS client, a speed test, a media server), is benign.
- In every case, what the client reached next: other traffic from `src` in `index=network` around the same time.

Don't name devices, addresses or the network layout beyond what the finding shows.

Skills: if a field looks missing or wrong (no `Answer`, `IP` empty), invoke `field-extraction-and-cim-mapping`; to work on the search itself, `search-and-dashboard-troubleshooter`.
