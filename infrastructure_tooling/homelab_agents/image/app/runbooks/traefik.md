# Web detections (Traefik access log: scanning, exploit attempt, authentication failures, new path)

Source: `index=network sourcetype=traefik:access`, Traefik's access log on k3s-01, one JSON line per request. Traefik routes only the tailnet-only hosts (apiary, auth, cribl, splunk, mcp and vault `.bmosan.com`): each has an allowlist for tailnet addresses, so a request comes from a tailnet device, or from the LAN to k3s-01's address and is refused with 403. The Cloudflare-tunnel apps don't pass through Traefik. Fields: `ClientHost` (the TCP peer, the finding's `src`; a client can't spoof it), `RequestHost` (`site`), `RequestMethod`, `RequestPath` (path and query), `DownstreamStatus` (what the client got), `OriginStatus` (what the backend answered; 0 means Traefik answered itself: allowlist 403, no route 404, backend down 502/503/504), `RouterName`, `ServiceName`, `request_User-Agent`, `request_Referer`. `request_Cf-Connecting-Ip` (`claimed_client_ip`) is whatever the client sent: never treat it as the source. Only those headers are logged; a payload in another header or in the body is not visible.

Check:
- Everything the client sent around the time: `index=network sourcetype=traefik:access ClientHost="<src>" earliest=-1h latest=+1h | table _time RequestHost RequestMethod RequestPath DownstreamStatus OriginStatus request_User-Agent | sort _time`, and whether it has done this before (look back 7 days).
- Who the client is: a tailnet address (100.64.0.0/10) is one of the user's own devices or a shared node; a LAN address got 403 from the allowlist unless the backend answered (`OriginStatus` > 0 means it reached the app). Other activity from `src` in `index=network` (DNS, firewall) and `index=infra` in the same window.
- Scanning: the sample paths. Dotfiles (`.env`, `.git`), WordPress or PHP pages and `../` on hosts that serve none of those are a wordlist. A security scanner the user runs on purpose looks the same: say which and suggest adding it to the `hl_web_scanner_allowed` macro in `85_detections` (set on the Splunk host, not in the repo).
- Exploit attempt: the payload and the status. 4xx means it was refused or failed; a 2xx or 3xx from the backend (`OriginStatus`) means the app accepted it, which matters most: look at that app's own logs (`index=k8s k8s.namespace.name=<namespace>` or `index=audit` for Vault and the MCP gateway) right after.
- Authentication failures: which endpoint and how fast. Many 401/403 on one API path with a script's user agent is guessing; a browser user agent polling one path every few seconds is an expired session in an open tab. Check the app's own audit (Vault audit `index=audit`, MCP gateway `toolhive:vmcp:audit`, Authentik events) for the identity tried.
- New path: what the path is in that app (an admin API, a debug endpoint, a page nobody opened before) and who reached it. A path the user opens after an upgrade or a new feature is benign.

Don't name devices, addresses or the network layout beyond what the finding shows.

Skills: if a field looks missing or wrong (`ClientHost` empty, no `RequestPath`), invoke `field-extraction-and-cim-mapping`; to work on the search itself, `search-and-dashboard-troubleshooter`.
