# Cloudflare account changes, logins, tunnels and firewall bursts

Source: Cloudflare's account audit log, `index=audit sourcetype=cloudflare:audit` (JSON: `action.description` such as "Create DNS Record" or "SSO_LOGIN", `action.type` create/update/delete/view, `action.result`, `actor.email`, `actor.type` user/account/system, `actor.context` dash/api/api_token, `actor.ip_address`, `actor.token.name`, `resource.product`, `resource.request` and `resource.response` (the API bodies), `zone.name`, `raw.uri`, `raw.user_agent`). Tunnel snapshots are `index=network sourcetype=cloudflare:tunnel` (`tunnel_name`, `status`, `connections`, `origin_ips{}`, `colos{}`), and blocked or challenged requests are `index=network sourcetype=cloudflare:firewall` (`clientIP`, `clientRequestHTTPHost`, `clientRequestPath`, `action`, `source`, `ruleId`, `userAgent`). A collector on the Splunk host pulls them every 10 minutes, so findings arrive 25 to 40 minutes after the change.

Cloudflare holds DNS, the tunnels that publish internal services, and Zero Trust for every public site, so a change here can redirect or expose anything. One owner runs the account. Normal: the owner editing DNS or tunnels in the dashboard (`actor.context=dash`, the owner's email, a residential address), cert-manager creating and deleting `_acme-challenge` TXT records with an API token (user agent `cert-manager-challenges/...`, already left out), Cloudflare itself renewing certificates (`actor.type=system`), and the collector's own token reading the audit log (views, never findings).

Check, for every audit finding:
- Who and from where: `user` (email, and the API token's name if one was used), `src`, and `via` (dash is the dashboard, api_token a script). The same address the owner used for other dashboard actions that day is a good sign; check with `index=audit sourcetype=cloudflare:audit actor.ip_address="<src>" earliest=-30d | stats count min(_time) max(_time) by actor.email actor.context`.
- What else that actor did in the hour around it: `index=audit sourcetype=cloudflare:audit actor.email="<user>" earliest=-1h latest=+1h | table _time action.description raw.uri zone.name`. A login from a new address followed by a token creation, a DNS change or a tunnel change is an account takeover pattern.
- Was it the owner's own planned work? Say so (expected_activity), unless it weakens something; then say what it weakened.

By detection:
- *API token or API key changed*: object is the token name, detail its permission groups. A token with edit permissions (DNS Write, Tunnel Write, Account Settings Write, Access Write) created by anyone but the owner in the dashboard, or from an unknown address, is an incident: roll or delete it. The Global API Key viewed or rolled is unusual in any case.
- *Account member, role or login settings changed*: a new member, a role change, or two-factor, SSO or password settings. The account has one person; a new member or 2FA being turned off is an incident unless the owner says otherwise.
- *DNS record changed*: object is zone: type name, detail the new content. High when an NS or MX record changed, or a record was repointed at a target not seen in DNS changes for 30 days. Does the new content belong to the homelab (the tailnet address 100.x, the home or LAN addresses other records use, a Cloudflare tunnel `<uuid>.cfargotunnel.com`)? A record pointing somewhere unknown can send a site's users or its mail elsewhere.
- *Tunnel or Zero Trust Access changed*: a tunnel created, deleted or reconfigured (detail lists the ingress hostnames: which public name now reaches which internal service), its connector token read, or an Access application, policy, group, identity provider or service token changed. A new ingress rule to an internal admin service, or an Access policy that allows everyone, exposes it to the internet.
- *Zone security setting weakened*: security level to low or off, SSL/TLS Off or Flexible, Always Use HTTPS or the WAF off, a WAF or rate-limit rule deleted or disabled, an IP allowlisted, Bot Fight Mode off. Ask whether it was a temporary troubleshooting change and whether it has been turned back (search the same zone and setting afterwards).
- *Dashboard login from a new IP or country*: the account owner's dashboard login from an address not seen in 30 days (high if the country is new too). Home addresses change after an ISP lease renewal; travel or a phone hotspot also explain it. What did the session do next (the same `src` in the audit log)? Failed logins (`results` not success) from abroad are someone trying the password.
- *Tunnel connector from a new origin address*: a tunnel's connector connected from a public address none of the tunnels used in 30 days. If every tunnel moved to the new address at once, the home address changed (expected). One tunnel connecting from somewhere else means someone else is running a connector with its token and can receive its traffic: rotate the tunnel token.
- *Firewall burst from one address*: one client blocked or challenged 50 times, or on 3 or more hostnames, in 15 minutes. Usually an internet scanner (paths such as `/wp-login.php`, `/.env`); Cloudflare already blocked it. Did any request from that address get through (`index=network sourcetype=cloudflare:firewall clientIP="<src>"` with action log or skip, or the origin's own access logs)? Blocked only is low risk; say so.

Don't name internal addresses, zones or the network layout beyond what the finding shows. Expected changes by the owner or by automation go in the `hl_cf_expected_change` macro on the Splunk host, never in the repo; recommend that rather than suggesting the detection be changed.
